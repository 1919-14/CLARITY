# Hypothesis Exploration and Evidence Interface

This document specifies the architecture, user workflows, API integration, comparability guards, and accessibility invariants for the CLARITY Hypothesis Exploration Interface (Issue #22).

---

## 1. Overview & Scientific Design

The interactive hypothesis exploration interface provides researchers with comprehensive inspection, comparison, and lifecycle management for competing explanations generated by CLARITY during discovery runs.

### Scientific Integrity Invariants

1. **Separation of Scientific Ranking from Workflow Flags**:
   - Scientific within-cohort ranking is computed server-side by the domain `HypothesisRanker` based on validated held-out predictive accuracy ($MAE$, $RMSE$) and structural parsimony (complexity).
   - Pinning (`is_pinned`) is purely a visual workflow preference for researcher convenience. It never modifies scientific scores or ranking.
   - Exclusion (`is_excluded`) removes a hypothesis from active selection cohorts without deleting its formula, revisions, or evaluation history.
   - The user interface renders scientific rank and workflow flags in distinct, visually separated columns.

2. **Honest Unavailable Metrics**:
   - Missing metrics (e.g. absent held-out evaluations, uncomputed RMSE, unevaluated candidates) are explicitly rendered as `Unavailable` / `—`.
   - Missing or pending values are **never** coerced or fabricated as zero (`0.00`).

3. **Protection of Ground Truth & Evaluator Internals**:
   - The interface displays candidate formulas, fitted parameters, observed values, predicted values, residuals, and dynamic tolerance thresholds.
   - Ground truth oracle implementation parameters and hidden evaluator generation rules are strictly inaccessible and never leaked to the client.

4. **Comparability Guard**:
   - Side-by-side comparison displays a prominent warning banner whenever compared candidates belong to differing evaluation tiers (e.g. `VALID_HELD_OUT` vs `VALID_TRAINING_ONLY` vs `EVALUATION_FAILED`) or differing dataset snapshot versions.

## 2. Interface Capabilities & Components

### 2.1 Hypothesis Explorer Table

Located at `/hypotheses?run=<run_id>`.

- **Multi-select Checkboxes**: Enables selecting multiple candidates for side-by-side comparison.
- **Candidate Identifiers**: Displays stable `hypothesis_id`, origin badge (`Researcher` vs `Agent`), current revision number, and last-updated timestamp.
- **Formulation & Parsimony**: Monospace formula code, model family, and structural complexity measure.
- **Scientific Assessment**: Displays within-cohort rank (`#1`, `#2`, or unranked), plausibility status badge (`PLAUSIBLE`, `UNCERTAIN`, `CONTRADICTED`, `UNEVALUATED`), and evaluation tier.
- **Predictive Error**: Displays held-out MAE/RMSE alongside training MAE/RMSE. Explains clearly that lower error values represent better predictive fit.
- **Workflow Flags**: Visual indicators for pinned and excluded states.
- **Actions**:
  - **Details**: Opens the comprehensive detail and evidence inspection modal.
  - **Pin / Unpin**: Toggles researcher visual bookmarking via `PATCH /api/v1/hypotheses/<id>`.
  - **Exclude / Restore**: Opens confirmation modal explaining exclusion behavior and submits with optional reason.
  - **Re-evaluate**: Enqueues/executes re-evaluation via `POST /api/v1/hypotheses/<id>/reevaluate`.

### 2.2 Filter and Sort Toolbar

- **Filter by Origin**: All, Agent generated, Researcher proposed.
- **Filter by Status**: All, Evaluated (`completed`), Pending, Failed, Unevaluated.
- **Filter by Lifecycle**: All, Active only, Pinned only, Excluded only.
- **Search Query**: Filters candidate IDs and mathematical formulas in real time.
- **Sort Options**:
  - Scientific rank (within-cohort rank)
  - Held-out MAE (ascending / descending)
  - Held-out RMSE
  - Training MAE
  - Structural complexity
  - Revision number
  - Recently updated timestamp

### 2.3 Side-by-Side Comparison View

- Opens in a modal when 2 or more candidates are selected.
- Compares formulas, model families, parameters, complexities, within-cohort ranks, plausibility statuses, evaluation tiers, held-out MAE/RMSE/R2, and dataset snapshot versions.
- **Comparability Guard Warning**: Flags when compared candidates were evaluated across differing tiers or dataset snapshots.

### 2.4 Candidate Detail & Evidence Modal

Contains four tabbed views:
1. **Overview & Metrics**: Full mathematical formula, fitted parameters JSON, model family, parsimony complexity, within-cohort rank, plausibility status, and predictive metrics for both training and held-out partitions.
2. **Evidence Observations**:
   - Queries `GET /api/v1/hypotheses/<id>/evidence`.
   - Displays summary badges: Supporting ($N$), Contradicting ($N$), Indeterminate ($N$).
   - Observation evidence table: Observation ID, Inputs ($x$), Observed ($y$), Predicted ($\hat{y}$), Residual ($|y - \hat{y}|$), Tolerance Threshold ($T$), Partition (`train`/`held_out`), and Classification badge.
   - Explains tolerance equation: $T = \tau_{\text{abs}} + \tau_{\text{rel}} \cdot |y_{\text{obs}}|$.
3. **Revisions Timeline**:
   - Queries `GET /api/v1/hypotheses/<id>/revisions`.
   - Displays past mathematical formulations, complexity, source, and change reasons.
4. **Evaluation History**:
   - Queries `GET /api/v1/hypotheses/<id>/evaluations`.
   - Displays timestamped evaluation runs, dataset versions, and error states.

### 2.5 Researcher Hypothesis Proposal

- Opens modal to submit new hypothesis via `POST /api/v1/runs/<run_id>/hypotheses`.
- Fields: Model family, mathematical formula, optional parameters JSON, optional complexity, optional custom ID.
- Client-side validation: Requires formula, verifies parameter JSON formatting and complexity bounds.
- Prevents duplicate submissions while in-flight.
- Displays backend validation errors in plain language.

## 3. Backend API Endpoints

| Method | Path | Description |
|---|---|---|
| `GET` | `/api/v1/runs/<run_id>/hypotheses?include_excluded=true` | Lists candidates with scientific rankings (`scientific_ranking`) attached via domain `HypothesisRanker`. |
| `POST` | `/api/v1/runs/<run_id>/hypotheses` | Proposes a researcher hypothesis. |
| `GET` | `/api/v1/hypotheses/<hypothesis_id>` | Retrieves single hypothesis record with latest evaluation and revisions. |
| `PATCH` | `/api/v1/hypotheses/<hypothesis_id>` | Updates flags (`is_pinned`, `is_excluded`) with optimistic concurrency (`expected_revision`). |
| `POST` | `/api/v1/hypotheses/<hypothesis_id>/reevaluate` | Enqueues/runs fresh candidate evaluation. |
| `GET` | `/api/v1/hypotheses/<hypothesis_id>/evidence` | Returns classified evidence observations and plausibility status. |
| `GET` | `/api/v1/hypotheses/<hypothesis_id>/revisions` | Returns revision history. |
| `GET` | `/api/v1/hypotheses/<hypothesis_id>/evaluations` | Returns evaluation history. |

## 4. Accessibility & Responsive Design

- Accessible semantic markup: Proper HTML5 tables with `<caption>`, `<th scope="col">`, `<th scope="row">`.
- Full keyboard navigation: Modal dialogs trap focus, close on Escape, and restore focus to triggering elements.
- Accessible ARIA attributes: `aria-modal="true"`, `aria-labelledby`, `aria-describedby`, `aria-busy`, `role="tab"`, `role="tablist"`, `aria-selected`.
- Readable monospace notation: Formula and parameter code blocks use legible high-contrast typefaces (`--font-mono`).
- Responsive layout: Adapts smoothly to narrow screens with horizontally scrollable tables and wrapped toolbars.
